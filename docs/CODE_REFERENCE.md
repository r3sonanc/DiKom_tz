# Как устроен проект

Это 2D-симуляция склада с диспетчером для нескольких роботов.
Роботы ездят по графу узлов и рёбер, диспетчер согласует переходы,
а браузер показывает состояние и отправляет команды оператора.
Инструкция запуска находится в [README](../README.md).

Для практического разбора откройте [путь одной команды](COMMAND_PATH.md):
термины, индикаторы связи, Firefox, ROS2 и номера строк исходников.
[Учебные копии](commented/README.md) поясняют каждую непустую строку кода.
[Проверки и оптимизация](VALIDATION.md) содержат замеры времени/памяти и команды тестов;
[безопасность](SAFETY.md) — обоснование защиты от столкновений и её предпосылки.

## 1. Что где находится

| Файл | Ответственность |
|---|---|
| `warehouse/map.py` | Две карты, парковки, стены, расстояния до графа |
| `warehouse/robot.py` | Кинематика, столкновения, команды, ошибки и общий мир |
| `warehouse/ros_simulator.py` | ROS-нода, которая продвигает физику и публикует состояния |
| `warehouse/dispatcher.py` | Совместное планирование, резервы, цели и режимы работы |
| `warehouse/transport.py` | ROS-обмен на стороне диспетчера |
| `warehouse/api.py` | HTTP API, WebSocket, цикл управления и подготовка данных для UI |
| `warehouse/static/` | HTML, CSS и JavaScript интерфейса, отрисовка в canvas |
| `launch/warehouse.launch.py` | Совместный запуск симулятора и диспетчера |

Два процесса запускаются как ROS-пакет `warehouse_sim`.
`SimulatorNode` создаёт ноду `/warehouse_simulator`, а `RosTransport` —
`/warehouse_dispatcher`. У нескольких роботов один общий физический мир,
но отдельные состояния, приказы и ошибки.

```text
Браузер → HTTP → FleetRuntime / Dispatcher → RosTransport
                                                ↓ /warehouse/commands
                                         SimulatorNode / WorldCore
                                                ↓ /warehouse/states
Браузер ← WebSocket ← FleetRuntime ← RosTransport
```

Команды и состояния передаются как JSON в `std_msgs/msg/String`.
Частоты: физика — 50 Гц, обычная телеметрия и контроллер — 10 Гц,
обновления браузера — 5 Гц. Браузер перерисовывает canvas отдельно.

Представление карты кэшируется при reset. Для WebSocket используется одна
сериализованная версия снимка на временной интервал до 100 мс с инвалидацией
после шага контроллера и операторских изменений. Сроки связи продолжают
обновляться без телеметрии. REST получает свежую независимую копию данных,
а `/metrics` читает счётчики без построения полного снимка.

## 2. Путь одной команды

Пример: отправить `robot1` в `r0c0`.

1. `app.js` отправляет `POST /api/robots/robot1/commands` с телом
   `{"type":"move","target":"r0c0"}`.
2. Модель `Command` проверяет тип и поля запроса; `Dispatcher.submit()`
   проверяет узел и конфликт целей, сохраняет цель и помечает план устаревшим.
3. `FleetRuntime.run()` раз в 0,1 с вызывает `step()`:
   принимает состояния, передаёт их в `Dispatcher.ingest()` и вызывает `tick()`.
4. Диспетчер строит согласованное расписание, затем выдаёт только очередной
   переход: `move` с `path: [исходный_узел, следующий_узел]` и `command_id`.
5. `FleetRuntime.send()` добавляет `world_id`; `RosTransport.send()`
   добавляет возрастающий `command_seq` и публикует команду.
6. `SimulatorNode._command()` передаёт JSON в `WorldCore.command()`.
   Мир проверяет свою ревизию и канал робота, затем вызывает `RobotCore.command()`.
7. `RobotCore.tick()` поворачивает робота и перемещает его к следующему узлу.
   По прибытии записывается `completed_command_id`.
8. Свежая телеметрия подтверждает переход. Когда завершены все переходы
   текущего раунда, диспетчер разрешает следующий.
9. `FleetRuntime._snapshot()` объединяет телеметрию, цели и резервы;
   `snapshot_json()` готовит общую строку, `/ws` отправляет её браузеру.

HTTP-ответ об успешном принятии команды означает назначение задачи.
Фактическое выполнение видно в последующих состояниях и метриках.

## 3. Карта и физика

`load_map()` поддерживает `normal` и `hardcore` по схемам задания.
Узел хранит ID, координаты в метрах и признак парковки.
Узлы `r{ряд}c{колонка}` образуют сетку с шагом 2 м; `p1`, `p2`, … — парковки.
На обычной карте три парковки, на сложной — пять. Роботы появляются на них.

`WarehouseMap.adjacency` задаёт разрешённые переходы, `edges` — рёбра,
`walls` — четыре внешние стены. `nearest_node()` ищет ближайший узел,
`distance_to_graph()` вычисляет расстояние до ближайшего ребра.
`segment_distance()` — общий геометрический помощник для этих расчётов.

`RobotCore` хранит координаты, угол, скорости, текущее ребро, приказ и ошибку.
Корпус изображается прямоугольником 0,8 × 0,6 м с двумя колёсами.
Для столкновений используется описанная окружность радиусом 0,5 м:
это консервативная оценка, которая работает при любом угле корпуса.

`_integrate()` рассчитывает движение по линейной и угловой скорости:
по прямой при нулевой угловой скорости, по дуге — при ненулевой.
Скорости колёс вычисляются из линейной скорости, угловой скорости,
расстояния между колёсами и радиуса колеса.
Автоматический режим сначала поворачивает к соседнему узлу, затем едет вперёд.
Ручной режим позволяет ехать назад и одновременно поворачивать.

`_collision()` проверяет стены и других роботов перед применением движения.
Проверяется участок перемещения, чтобы не перескочить сквозь другого робота.
Большой шаг времени ограничивается 0,1 с и делится на подшаги до 0,02 с.

`RobotCore.command()` отдельно проверяет существование точек,
соседство узлов и положение робота относительно графа.
Продолжить прерванное автоматическое ребро можно с сохранённой позиции на нём.
Ошибка останавливает скорости и остаётся в телеметрии.

Основные ошибки: `POINT_NOT_FOUND`, `INVALID_PATH`, `NOT_AT_NODE`,
`OFF_GRAPH`, `STUCK`, `COLLISION_WALL`, `COLLISION_ROBOT`, `INVALID_COMMAND`.
Плохая цель из UI обычно отклоняется API раньше, чем попадёт в симулятор.

## 4. Как роботы делят пути

`CooperativePlanner` ищет пути в пространстве состояний `(узел, шаг)`.
Один шаг означает переход в соседний узел или ожидание на месте.
Расстояния BFS используются как эвристика для A*.

Планировщик последовательно строит пути роботов, учитывая уже выбранные.
Для каждого перехода резервируются оба конца ребра на соответствующий шаг.
Это запрещает совместное занятие узла, встречный обмен по одному ребру
и слишком близкое следование. При неудаче перебираются порядки приоритетов.

Путь вида `[A, A, B]` означает «подождать, затем перейти в B».
После достижения цели робот продолжает занимать её в оставшейся части плана.
Итоговые пути дополняются ожиданием до одинаковой длины.

Глубина поиска ограничена `3 × число_узлов + число_роботов²`,
общий бюджет — 300 000 раскрытий. Если поиск не справился,
диспетчер показывает причину ожидания и не выдаёт опасный переход.

В `Dispatcher` важно различать структуры задач и резервов:

| Поле | Что содержит |
|---|---|
| `goals` | Конечные цели задач |
| `_schedule` | Согласованные последовательности узлов |
| `_round` | Уже разрешённые переходы, ожидающие подтверждения |
| `_held` | Переходы неисправных роботов, ресурсы которых нужно сохранить |
| `RobotRecord.protected_resources` | Последний разрешённый участок, удерживаемый при потере связи или reboot |
| `RobotRecord.protected_command` | Последний разрешённый приказ для проверки возвращённой телеметрии |

Шаг плана не равен секунде: реальное движение может занять больше времени.
`tick()` повторяет команды текущего раунда и ждёт телеметрии о прибытии
всех его участников. Независимые переходы идут параллельно.
Новое назначение не отменяет уже занятые ресурсы посреди перехода.

`_resources()` объединяет фактический узел, концы текущего ребра
и пути из `_round`/`_held`. В `_build_schedule()` ресурсы неисправного робота
попадают в заблокированные узлы. Поэтому остановившийся посреди ребра
робот сохраняет оба его конца занятыми без произвольного тайм-аута.

`_choose_endpoints()` подбирает место для уступания роботу без активной цели,
если его текущий узел нужен другому. Если общий план не найден,
операторские задачи могут выполняться поэтапно.
Повтор одинакового неудачного поиска ограничен интервалом в секунду.

`park` выбирает доступную парковку с учётом целей и резервов;
если робот находится в узле, выбирается ближайшая по графу.
`_assign_random_goals()` для «Тёмного цеха» выбирает случайный узел
из дальней трети достижимых кандидатов, исключая уже назначенные цели.
После завершения задачи назначается следующая; при неудаче поиска
случайные цели могут быть перевыбраны.

## 5. Обмен и потеря связи

Диспетчер не предполагает, что отправленная команда обязательно дошла.
Движение подтверждается телеметрией; безопасность поддерживается
на обеих сторонах канала.

| Механизм | Для чего нужен |
|---|---|
| `command_id` | Повтор текущей команды продлевает её действие без повторного старта |
| `command_seq` | Запоздалая старая команда не отменяет более новую остановку |
| Lease автоматического движения 0,9 с | Робот сам останавливается без продления команды |
| Lease ручного движения 0,35 с | Робот останавливается при исчезновении управления |
| Heartbeat 1,5 с | Диспетчер перестаёт считать старую позицию свежей |
| `seq` и `boot_id` | Отбрасываются повторы состояний и обнаруживается перезапуск робота |
| `world_id` и `reset_seq` | Сообщения прошлого мира и старый reset не заменяют новую сцену |

При отсутствии свежей телеметрии хотя бы одного робота весь парк замораживается.
`_mark_offline()` переводит известного робота в `OFFLINE`, сохраняет последний
разрешённый участок через `_protect()` и включает защитную остановку.
Если отправленный `stop` не дошёл, lease робота всё равно прекратит движение.

Первое свежее принятое состояние после потери связи даёт `RECOVERING`,
а не немедленное разрешение ехать. `_recovery_problem()` проверяет свежесть,
остановку, ошибки, узел/ребро, конечные координаты, текущий приказ и конфликты
ресурсов. Подтверждение в `_confirm_recovery()` допускает `ONLINE` и завершает
уже выполненный переход без повторного запуска. Флот продолжает движение,
когда все участники подтверждены и оператор не оставил его на паузе.

Изменение `boot_id` сохраняет старые резервы вместе с новым сообщённым положением
и требует явного `resume`. `recovery_ready` разрешает оператору подтвердить
безопасное продолжение, но не запускает его автоматически. Миссия сохраняется;
после подтверждения узла старый переход заменяется планом из известного положения.
Подробные предпосылки и исключение для ручного возврата с `OFF_GRAPH` — в [SAFETY.md](SAFETY.md).

`RosTransport` принимает ROS-сообщения в отдельном потоке.
Под блокировкой сохраняется только последнее состояние каждого робота;
управляющий цикл забирает эти состояния без очереди старой телеметрии.
Команды имеют QoS `RELIABLE` и срок жизни сообщения 0,5 с,
состояния — `BEST_EFFORT`. Проверки приложения дополняют настройки DDS.

`WorldCore` позволяет имитировать сбои отдельно для каждого робота:

- `stuck` — ошибка и блокировка движения;
- `link_lost` — прекращение обычных команд и телеметрии;
- `throttle` — приём обычных команд и публикация состояний не чаще раза в секунду.

Управляющая команда изменения отказа обрабатывается отдельно,
чтобы имитацию потери связи можно было выключить из UI.
Устранение застревания и сброс ошибки — разные действия:
`clear_error` проверяет препятствия и положение, прежде чем разрешить работу.

`Dispatcher.drain_events()` передаёт API ограниченную очередь переходов состояния.
`FleetRuntime.drain_dispatcher_events()` превращает их в UTC-логи и привычные
сообщения журнала UI. Регистрируются потеря/возврат связи, защитная остановка,
reboot, ошибка/подтверждённый сброс, возобновление и отказ планирования.
Дубликаты телеметрии отвергаются до учёта событий. Начальное ожидание первой
телеметрии не считается потерей; `LINK_RECOVERED` означает возврат сообщений,
а не обязательно завершённую проверку `RECOVERING`.

## 6. Ручное управление и остановка

`stop` ставит весь парк на паузу. `resume` проверяет ошибки и возможность
безопасно продолжить движение. Сохранённое автоматическое ребро можно
продолжить; после свободного ручного движения нужно вернуться к узлу.

При `manual` диспетчер приостанавливает автоматику всех роботов.
Ручное движение разрешается после остановки остальных и выдержки lease.
Одновременно управлять вручную можно только одним роботом.

`app.js` отправляет скорости при изменении клавиш и каждые 100 мс
при удержании. W/S задают линейную скорость ±0,5 м/с,
A/D — угловую ±1,25 рад/с. Отпускание клавиш, потеря фокуса,
скрытие страницы и Escape отправляют нулевую скорость.
На случай обрыва браузера остаются тайм-ауты диспетчера и робота.

Если робот оказался далеко от графа, автоматическая поездка отклоняется.
Нужно вернуть его вручную к узлу и, если есть ошибка, сбросить её.
Для `clear_error` допускается привязка к ближайшему свободному узлу
с расстояния до 0,2 м; сохранённое ребро обрабатывается отдельно.

## 7. API и состояние

| Метод и путь | Назначение |
|---|---|
| `GET /` | Веб-интерфейс |
| `GET /api/health` | Service health в HTTP-коде и отдельный блок состояния флота |
| `GET /api/state` | Полный снимок мира |
| `POST /api/reset` | Новая карта и число роботов |
| `POST /api/robots/{id}/commands` | `move`, `park`, `stop`, `manual`, `resume`, `clear_error` |
| `POST /api/robots/{id}/faults` | Имитация отказов |
| `POST /api/dark-factory` | Включение/выключение случайных заданий |
| `GET /metrics` | Числовые метрики в текстовом формате Prometheus |
| `WS /ws` | Поток снимков мира |

`StrictModel` запрещает неизвестные поля и нечисловые значения NaN/Infinity.
`Reset` ограничивает число роботов диапазоном 1–5;
`FleetRuntime.reset()` дополнительно проверяет число парковок выбранной карты.
До начальной телеметрии команды движения возвращают HTTP 409.

Состояние робота содержит позицию, угол, линейную/угловую скорости,
узел или ребро, текущий приказ, ошибку и давность последнего сообщения.
`connected` остаётся признаком свежей телеметрии. `link_state` различает
`ONLINE`, `OFFLINE`, `RECOVERING`; `recovery_reason` объясняет удержание,
`recovery_ready` разрешает явный resume, `position_stale` отмечает неподтверждённую позу.
`availability` дополнительно учитывает `ERROR` и `PAUSED`, не заменяя старое `state`.
Снимок также содержит карту, цели, резервы, причину ожидания и метрики.
Журнал API ограничен 100 событиями, история команд робота — 256 записями,
таблица ревизий транспорта — 1024. Ранее завершённые `boot_id` хранятся
до смены мира, поэтому не вся история ограничена фиксированным числом записей.

`FleetRuntime.health()` отделяет готовность HTTP/контроллера/ROS от состояния флота.
После начальной синхронизации свежая телеметрия хотя бы одного робота менее
трёх секунд назад, работающие контроллер и транспорт дают HTTP 200. Частичный
OFFLINE отражается в `fleet` и включает защитную остановку, но не делает HTTP
сервер неработающим. Нет данных от всех более трёх секунд или не работает транспорт/
контроллер — HTTP 503. Сохраняются `ok`, `world_id`, `transport`; добавлены
`controller`, `service` и `fleet` с online/offline/recovering/errors/safety_stop.

Новые `/metrics`: `warehouse_link_loss_events_total`, `warehouse_link_recovery_events_total`,
`warehouse_offline_robots`, `warehouse_fleet_safety_stops_total`, `warehouse_robot_errors_total`,
`warehouse_planning_duration_seconds`, а также его `_sum` и `_count`.
Последние три поля описывают фактические попытки построения расписания вместе
с поэтапными попытками. Ошибки и сетевые события считаются при изменении состояния.
Структурированный лог имеет вид `UTC | LEVEL | robot_id | CODE | reason`;
добавочные поля журнала `code`, `robot_id`, `reason` сохраняют прежние time/level/message.

## 8. Как объяснить и показать решение

Короткий рассказ: «Симулятор отвечает за физику и самостоятельную остановку,
диспетчер — за цели и согласованные переходы. ROS2 связывает два процесса,
FastAPI предоставляет управление и снимки состояния браузеру.
Маршруты планируются с ожиданиями, а переходы подтверждаются телеметрией».

Для демонстрации:

1. Создайте обычный склад с одним роботом: поездка, поворот, парковка.
2. Покажите WASD, движение назад и остановку при отпускании клавиш.
3. Создайте склад с несколькими роботами и включите «Тёмный цех».
4. Переключитесь на «Узкие коридоры»: покажите ожидание и разъезд.
5. Во время движения включите застревание: участок остаётся занят.
   Снимите застревание и сбросьте ошибку.
6. Включите потерю связи: робот остановится по lease, остальные будут ждать.
   Покажите OFFLINE, последнюю позицию и сохранённые резервы. Восстановите связь:
   сначала RECOVERING, затем продолжение после проверки остановки и положения.
7. Покажите замедление связи, `/api/state`, `/metrics` и ROS-ноды
   командами из README.
8. Для сценария reboot используйте регрессионный тест из набора восстановления:
   смена `boot_id` посреди перехода должна оставить RECOVERING и явную паузу.
   Объясните, почему `recovery_ready` ещё требует команды оператора.

Что полезно уметь объяснить:

- Почему независимых кратчайших путей мало: они не учитывают одновременные
  конфликты. Здесь поиск добавляет время, ожидания и резервы.
- Почему раунд завершается по подтверждениям: длительность поворота и доставки
  сообщений заранее неизвестна.
- Почему нельзя освободить резерв по таймеру: молчание робота не доказывает,
  что он физически освободил участок.
- Зачем lease при наличии `stop`: по оборванному каналу `stop` может не дойти.
- Почему физика общая: столкновения требуют согласованного состояния мира;
  это не мешает отдельным приказам и телеметрии каждого робота.

## 9. Границы решения

Физика кинематическая: нет масс, проскальзывания, датчиков и локализации.
Gazebo не используется; 2D разрешён уточнениями к заданию.
ROS2 в рабочем запуске настоящий: процессы общаются через DDS.

Поиск ограничен бюджетом и глубиной, поэтому может не найти существующий путь.
Поддерживаются две небольшие карты и до пяти роботов.
Отсутствие любых тупиков для любых целей математически не гарантируется.
Если неисправный робот перекрыл единственный проход, его нужно освободить.

Полный VDA5050 и MQTT не реализованы: заимствована идея приказов,
состояний и разрешённых участков, но JSON-контракт и транспорт собственные.
Нет базы данных, восстановления задач после рестарта и аутентификации.
Для одной сцены предполагается один диспетчер; Compose публикует веб-порт
только на localhost для локальной демонстрации.
