# Безопасность движения и границы гарантий

Здесь описано, за счёт чего симулятор удерживает роботов от пересечения,
что проверяют автотесты и какие предпосылки нужны для этого утверждения.
Результаты конкретных прогонов и проверка среды находятся в [VALIDATION.md](VALIDATION.md).

`normal` — обычный склад, `hardcore` — внутреннее имя карты **«Узкие коридоры»**.
Внешнее имя карты не меняет алгоритм безопасности: обе карты проходят одни проверки.

## Два уровня защиты

**Диспетчер согласует движение по графу.** В [dispatcher.py](../warehouse/dispatcher.py)
планировщик рассматривает состояние «узел и шаг». Для перехода резервируются
оба конца ребра. Другой робот не получает конфликтующий переход на том же шаге;
ожидание на узле тоже занимает ресурс. Поэтому план учитывает встречный проезд,
совместное занятие узла и необходимость уступить дорогу.

Разрешённые переходы находятся в `_round`. Следующий раунд начинается после
подтверждения текущих переходов телеметрией, а не по предполагаемой длительности
поездки. Неисправный робот сохраняет ресурсы своего перехода в `_held`.
Истечение времени само по себе не освобождает занятый участок.
При потере связи `RobotRecord.protected_resources` дополнительно сохраняет
последние известные узел/ребро и разрешённый переход. Пока положение не проверено,
`_resources()` объединяет эти резервы с новым сообщённым положением.

На двух заданных картах рёбра без общих конечных узлов имеют достаточный
геометрический зазор для корпусов. Это отдельное свойство карт, проверяемое тестом.
При добавлении произвольных пересекающихся рёбер одного резервирования узлов
может оказаться мало: геометрию новой карты тоже нужно проверять.

**Симулятор проверяет само перемещение.** В [robot.py](../warehouse/robot.py)
`RobotCore._integrate()` сначала вычисляет предполагаемое новое положение,
потом вызывает `_collision()` и только после успешной проверки меняет координаты.
При отказе координаты сохраняются, скорости обнуляются и появляется ошибка.
Та же защита применяется перед доводкой к конечному узлу и при сбросе ошибки.

Геометрический слой полезен и в ручном режиме, где движение не ограничено
рёбрами графа. Его работа не зависит от того, нашёл ли диспетчер хороший маршрут.

## Какая геометрия используется

Робот изображён прямоугольником 0,8 × 0,6 м. Для проверки столкновений используется
описанная окружность радиуса `R = 0,5 м`. Если эти окружности не пересекаются,
прямоугольные корпуса тоже не пересекаются при любом угле поворота.
Такая оценка консервативна: иногда она остановит робота раньше, чем столкнулись бы
точные прямоугольники.

Стены — четыре границы прямоугольной области склада. Внутренние стеллажи
или произвольные препятствия физическая модель не содержит.

`tick()` ограничивает обрабатываемый интервал 0,1 с и делит его на подшаги
не более 0,02 с. При ограничениях `|v| ≤ 0,8 м/с`, `|ω| ≤ 1,8 рад/с`
поворот за подшаг не превышает 0,036 рад.

Для прямого движения проверяется весь отрезок от старого центра до нового,
а не только конечная точка. Для движения по дуге добавляется запас:

```text
p = |v × ω| × h² / 8
```

Здесь `h` — длительность подшага. Максимальное отклонение короткой дуги от хорды
не превышает этого запаса: `|v/ω| × (1 − cos(|ωh|/2)) ≤ p`.
Поэтому достаточно проверить коридор вокруг хорды, расширенный на `p`.
При нулевой угловой скорости используется прямая, запас равен нулю.

Для стен учитываются минимальные и максимальные координаты **обоих концов**
хорды с радиусом `R + p`. Для другого неподвижного центра проверяется расстояние
до всего отрезка; порог равен `2R + p + 1e-9 м`.
Положительный численный запас выбран в безопасную сторону: почти касающийся
шаг может быть отклонён. Он не является расчётом ошибок всех операций с плавающей
точкой и не заменяет формальную численную верификацию.

## Почему сохраняется безопасное состояние

Это обоснование относится к реализованной последовательной модели мира.

1. При создании стандартной сцены роботы стоят на разных парковках.
   Корпуса находятся внутри стен, расстояния между центрами превышают `2R`.
2. `WorldCore` изменяет положение одного робота за раз. При проверке его
   перемещения остальные центры считаются фиксированными.
3. Принятый подшаг имеет проверенный коридор движения. Он не пересекает стены
   и описанные окружности остальных роботов.
4. Смена координат при доводке к узлу и сбросе ошибки также проходит проверку.
   Остановка, истечение lease и установка ошибки сами координаты не меняют.
5. Следовательно, при выполнении предпосылок каждый следующий принятый шаг
   сохраняет непересечение в этой модели. Отказ шага сохраняет предыдущее положение.

Это объясняет инвариант, проверяемый тестами, но не объявляет проект формально
верифицированной системой для любого ввода или реального оборудования.

## Предпосылки

- Используются две штатные карты, корректная начальная сцена и конечные числовые
  координаты, скорости и времена.
- У роботов уникальные ID. В проверку передаются все остальные роботы этого мира.
- Координаты меняет один последовательный исполнитель `WorldCore`; внешнего
  изменения полей, телепортации или параллельной записи в физический мир нет.
- Сценой управляет один диспетчер. Штатный HTTP API проверяет команды и допускает
  ручное управление только одним роботом одновременно.
- Ограничения скоростей, подшагов и геометрические проверки не отключены.
- При добавлении карт, форм корпусов или новых способов перемещения предпосылки
  и тесты пересматриваются.

Отдельно важно различать последовательный расчёт и воображаемую одновременную
интерполяцию всех позиций между двумя снимками. `WorldCore` последовательно
применяет движения и проверяет каждое из них. Он не решает задачу непрерывного
синхронного движения произвольных нескольких ручных траекторий.
Публикация конкурирующих raw ROS-команд в обход единственного диспетчера
выходит за поддерживаемый сценарий управления.

## Потеря связи, ошибки и новая сцена

Диспетчер считает телеметрию устаревшей после 1,5 с без принятого свежего состояния.
В этом случае весь парк замораживается, остановки повторяются, резервы сохраняются.
Продолжение остальных роботов с локальной блокировкой здесь не реализовано.

Свежесть определяется не одним возрастающим `seq`: API требует конечный числовой
`sim_time`. В протоколе это отметка монотонных часов хоста в момент создания
состояния, а не прошедшее время физической симуляции. Принимается состояние
возрастом не более 0,5 с и не более чем на 0,1 с из будущего; в пределах одного
`boot_id` отметка не может уменьшаться. Heartbeat отсчитывается от
`min(sim_time, время_приёма)`, поэтому доставка старой очереди с новыми `seq`
не продлевает доступность робота до времени её получения.

Эта проверка предполагает общие монотонные часы: в текущем развёртывании
симулятор и диспетчер работают в одном ядре ОС. Синхронизация часов разных
хостов и аутентификация отправителя не реализованы. Произвольные задержки,
поддельные временные отметки и реальное оборудование не входят в гарантию.

У робота есть независимый lease: без продления автоматическое движение
останавливается через 0,9 с, ручное — через 0,35 с.
Так робот остановится и тогда, когда команда `stop` не смогла пройти по каналу.

Состояния связи отделены от ошибок и операторской паузы:

| Состояние | Значение и условия выхода |
|---|---|
| `ONLINE` | Телеметрия свежая, положение подтверждено; обычные правила управления действуют |
| `OFFLINE` | Нет свежей принятой телеметрии; последнее разрешённое ребро и узлы сохраняются |
| `RECOVERING` | Свежие сообщения вернулись, но остановка/положение/приказ ещё проверяются; обычное движение не разрешено |

Первое свежее сообщение после потери связи переводит робота в `RECOVERING`.
Проверяются последовательность и `boot_id`, отсутствие ошибки, подтверждённая
остановка, корректность заявленных узла/ребра и координат, принадлежность
последнему разрешённому участку, активный приказ и занятость другими роботами.
Неизвестный приказ, другое ребро, противоречащие координаты или ошибка сохраняют
защитную остановку. Само значение `connected: true` означает только свежесть сообщений.

При возврате того же запуска проверенное положение разрешает завершить
восстановление. Весь флот продолжает работу только после подтверждения свежей
остановленной телеметрии всех участников и при отсутствии операторской паузы.
Если переход уже завершён, диспетчер подтверждает прибытие вместо его повторной
выдачи. Если робот остановился на разрешённом ребре, продолжение получает новый
ID разрешения, сохраняя исходную миссию и безопасный участок.
Подтверждение `_confirmed_arrivals` связано с точным `command_id` разрешения:
прибытие по старой команде после reboot не может завершить новый переход.

Изменение `boot_id` даёт `RECOVERING`, явную паузу и событие `ROBOT_RESTARTED`.
До проверки и команды оператора сохраняется объединение старых резервов и нового
сообщённого положения. `recovery_ready: true` показывает возможность нажать
«Возобновить», но само по себе движение не запускает. `resume` повторно проверяет
свежесть и безопасность всего флота. После подтверждения известного узла разрешается
перепланирование сохранённой миссии; старый разрешённый переход не запускается заново.

Застревание не означает исчезновение робота с участка. Снятие причины отказа
и разрешение продолжить работу разделены: `clear_error` проверяет положение
и препятствия. Сохранённый переход позволяет восстановиться без освобождения
ресурсов по произвольному таймеру.

Ручной режим сначала приостанавливает автоматику остальных роботов и ждёт
подтверждения остановки с учётом lease. Для возвращения к автоматической работе
после свободного ручного движения требуется известное положение на графе.
Для уже активного ручного восстановления предусмотрен узкий случай: тот же запуск,
свежая остановленная телеметрия, конечные координаты внутри склада и ошибка
`OFF_GRAPH` допускают вернуть робота к узлу вручную. Это не разрешение продолжить
автоматический маршрут: пауза и ошибка сохраняются, автоматический `resume`
требует возврата к узлу и сброса ошибки. Иные ошибки блокируют восстановление.

Интерфейс отмечает OFFLINE/RECOVERING как последнюю или неподтверждённую позицию,
а не как гарантированное фактическое положение. Резервы — запрещённые для выдачи
ресурсы графа, они не являются измеренной позой робота. Потеря самого WebSocket
показывается отдельно от потери связи с конкретным роботом.

`world_id` отделяет сообщения новой сцены от старой; `reset_seq` запрещает
запоздалому reset заменить более новый мир. Reset создаёт новую допустимую
расстановку на парковках. Это явная замена сцены, а не физическое перемещение
роботов через весь склад. `command_seq`, `seq` и `boot_id` отдельно защищают
порядок приказов, телеметрии и смену запуска робота.

Эти механизмы относятся к симуляции. Они не моделируют тормозной путь,
ошибки датчиков, запаздывание приводов и аппаратную аварийную остановку.
Используются собственные JSON-сообщения поверх ROS2, без полной реализации
VDA5050. Состояние и история запуска живут в оперативной памяти; восстановления
миссий после перезапуска процесса по постоянному хранилищу нет.

События и метрики подтверждают переходы состояний, но не управляют движением.
Счётчик возврата связи растёт при первом свежем состоянии после OFFLINE,
даже если робот ещё RECOVERING. Отдельные счётчики защитных остановок и ошибок
не растут от каждого тика или повторной телеметрии. Записи UTC-логов соответствуют
изменениям состояния, а не подменяют проверку фактического положения.

## Три регрессии, найденные аудитом

Для этих случаев добавлены точечные автотесты. Позиции задаются непосредственно
в тестовом мире, чтобы воспроизвести граничный случай без долгой поездки.

| Случай | Пример до исправления | Что исправлено |
|---|---|---|
| Дуга у стены | Старт `(4; 0,500009)`, угол `−0,009`, `v=0,8`, `ω=1,8`, `h=0,02`: конечная точка внутри, но минимум дуги `y≈0,499991` меньше радиуса `0,5` | Проверяются оба конца хорды с запасом дуги |
| Отрицательный допуск | Центры `(4; 4)` и `(5,016−5e−10; 4)`; первый едет прямо на `0,016 м`: прежний порог разрешал расстояние `0,9999999995` | Численный запас изменён в консервативную положительную сторону |
| Доводка к узлу | Первый центр `(6−8e−8; 6)`, второй `(7−4e−8; 6)`: безопасный старт, но присваивание первому `x=6` создавало пересечение | Перед доводкой выполняется геометрическая проверка |

Тесты движения используют независимые геометрические проверки отрезков и дуг,
а не вызов проверяемой `_collision()` как единственный источник истины.
Дополнительно проверяются планы, стандартные карты, разные начальные значения
генератора, отказы и восстановление.

Конечный набор успешных прогонов подтверждает проверенные сценарии и защищает
от повторного появления ошибок. Он не перебирает все вещественные координаты,
все последовательности сообщений и все возможные исполнения программы.
Поэтому число тестов и пройденные модельные часы не превращаются в универсальное
доказательство отсутствия любых столкновений.

## Безопасность и выполнение задач

Безопасная остановка сохраняет расстояния, но может прекратить поток заданий.
Если неисправный робот перекрыл единственный проход, остальным некуда его объехать.
Ограниченный поиск тоже может не найти существующий маршрут.

Для текущего ТЗ проверяются поездки и разъезд на заданных картах, уступание,
удержание занятого участка и безопасное восстановление. Универсальная гарантия
выполнения любых целей без ожидания не заявляется.
Для снятия этих ограничений понадобятся другие требования к картам,
политике резервирования и алгоритму совместного планирования.

## Сложность после кэширования API

Обозначения: `V` — узлы, `E` — рёбра, `R` — роботы, `H = 3V + R²` — горизонт,
`Δ` — максимальное число соседей узла, `C` — WebSocket-клиенты, `L` — журнал.
`D` обозначает размер полного снимка, включая карту, маршруты и журнал:
порядка `V + E + RH + L` при ограниченной длине отдельных полей.

Координация, перебор приоритетов и геометрические проверки сохранены.
Кэши сокращают повторную работу подготовки API, не меняя поиск маршрутов.

| Участок | Время | Дополнительная память / пояснение |
|---|---|---|
| Матрица BFS при создании планировщика | `O(V(V+E))` | `O(V²)` |
| Один поиск A* по узлу и шагу | В грубой верхней оценке `O(VH(Δ+1) log(VH) + H(V+R))` | `O(VH)` для состояний и временной занятости |
| Перебор приоритетов | До `R!` порядков, в каждом до `R` поисков | `permutations` ленивый: таблица из `R!` порядков не хранится |
| Геометрические проверки всех роботов за подшаг | `O(R²)` | Без пространственного индекса; координаты `O(R)` |
| Представление карты для API | `O(V+E)` один раз на reset | `O(V+E)` на текущую сцену |
| Свежий независимый снимок для REST | `O(D)` | Копирование не даёт вызывающему менять внутренний кэш |
| Подготовка общей JSON-версии и передача ссылок `C` клиентам | `O(D+C)` на общую версию | Одна кэшированная JSON-строка `O(D)` |
| Реальная доставка этой версии всем клиентам | `Θ(CD)` байт | UTF-8-кодирование, копирование и сетевые буферы остаются на стороне соединений |

Общий кэш хранит одну версию, а не историю снимков. Он инвалидируется при изменении
состояния и обновляется по времени: устаревание телеметрии продолжает отражаться
даже при отсутствии новых сообщений. Каждый клиент отправляет данные самостоятельно;
тайм-аут отправки не даёт одному зависшему соединению останавливать остальных.

Память состояний поиска, матрицы расстояний и расписаний имеет порядок
`O(V² + VH + RH)`, без учёта ограниченных журналов и истории запусков.
`retired_boots` растёт с числом перезапусков до смены мира; его нельзя молча считать
константой для бесконечно долгой сцены.

При наличии клиентов дополнительно нужны общая JSON-строка `O(D)` и память
соединений. В худшем случае отправляемые данные и буферы могут занимать `O(CD)`;
кэш общей строки не устраняет эту часть памяти.

Бюджет 300 000 раскрытий ограничивает работу A*, но не является строгим пределом
времени: создание таблиц занятости и ранние отказы тоже требуют вычислений.
При пяти роботах приоритетов не больше 120. Пространственный индекс не улучшил бы
худший случай `O(R²)` и добавил бы обслуживание структуры.
Независимое продвижение без общего раунда изменило бы саму координацию.
Эти изменения требуют подтверждённой потребности и отдельной проверки, поэтому
в текущую оптимизацию API они не входят.
