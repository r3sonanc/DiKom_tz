# Протоколы

## ROS2

Оба топика используют `std_msgs/msg/String` с JSON. Это минимальный читаемый контракт, которому не нужна отдельная сборка `.msg`. При росте системы его следует заменить типизированными сообщениями ROS; сейчас поля проверяются на входе.

| Топик | QoS | Назначение |
|---|---|---|
| `/warehouse/commands` | RELIABLE, VOLATILE, KEEP_LAST 100, lifespan 0.5 с | Команды и продление lease |
| `/warehouse/states` | BEST_EFFORT, KEEP_LAST 10 | Текущее состояние, обычно 10 Гц на робота |

Физика работает на 50 Гц, диспетчер — около 10 Гц, браузер получает снимки около 5 Гц. BEST_EFFORT выбран для свежести состояния; потеря одного сообщения не должна накапливать очередь устаревших координат. Подробнее: [официальное описание QoS ROS2 Jazzy](https://docs.ros.org/en/jazzy/Concepts/Intermediate/About-Quality-of-Service-Settings.html).

Команда одного перехода:

```json
{"world_id":"...","robot_id":"robot1","command_id":"dispatch-12","command_seq":12,"type":"move","path":["p1","r1c5"]}
```

`stop`, `manual` (поля `linear`, `angular`), `clear_error` используют те же идентификаторы. При повторе одного и того же приказа сохраняются ID и sequence. Новый приказ должен иметь больший `command_seq`; устаревший не оживит движение после остановки. Телеметрия содержит `robot_id`, `world_id`, `boot_id`, `seq`, `pose`, `velocity` (включая скорости колёс), `node_id`, `edge`, `current_order`, `status`, `error`, `completed_command_id` и информацию об имитации отказов.

Приказ `reset` — административный: `world_id`, `reset_seq`, `map`, `robots`. Один диспетчер формирует возрастающий `reset_seq`; повтор текущего reset идемпотентен, старый не возвращает предыдущий мир. Несколько одновременно управляющих диспетчеров не поддерживаются.

`fault` — административная имитация отказа с `robot_id` и булевыми полями `stuck`, `link_lost`, `throttle`. Она проходит независимо от моделируемого канала робота, чтобы канал можно было восстановить. `link_lost` блокирует и команды, и телеметрию. `throttle` ограничивает оба направления до 1 Гц, то есть ниже частоты продления lease. Робот может кратко останавливаться, но ресурс не освобождается.

Симулятор намеренно сообщает `POINT_NOT_FOUND`, `INVALID_PATH`, `OFF_GRAPH`, `NOT_AT_NODE`, `STUCK`, `COLLISION_WALL`, `COLLISION_ROBOT` и ошибки формата. HTTP заранее отклоняет неизвестную цель; независимая проверка на роботе остаётся для прямых ROS-команд.

## HTTP и WebSocket

| Метод / путь | Тело / результат |
|---|---|
| `GET /api/health` | 200 после получения начального состояния, до этого 503 |
| `GET /api/state` | Полный текущий снимок |
| `WS /ws` | Снимки без накопления очереди событий |
| `POST /api/robots/{id}/commands` | `{type:move,target:node}` либо `park`, `stop`, `resume`, `clear_error`, `manual` |
| `POST /api/robots/{id}/faults` | Изменяемые булевы `stuck`, `link_lost`, `throttle` |
| `POST /api/dark-factory` | `{enabled:true/false}` |
| `POST /api/reset` | `{map:normal/hardcore,robots:1..3/5}` |
| `GET /metrics` | Числовые метрики в текстовом формате Prometheus |

Фактическая JSON-схема доступна через `/docs`. Неподдерживаемые поля, NaN/Infinity и скорости вне границ отклоняются. Нет аутентификации и сохранения заказов в БД: приложение рассчитано на локальную демонстрацию, опубликовано на localhost и не требует внешних сервисов.

## Связь с VDA5050

[Официальная спецификация VDA5050](https://github.com/VDA5050/VDA5050) разделяет управление флотом и исполнение приказа роботом. Здесь сохранены полезные для задания идеи: ID приказа, последовательность, узлы/рёбра, отчёт состояния и разрешение следующего безопасного участка. JSON-схемы VDA и его MQTT-транспорт не реализованы; произвольный VDA-клиент к этому приложению не подключится.
