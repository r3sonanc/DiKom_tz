# Фактическая проверка

Проверено 23 октября 2026 года. Рабочая среда проверки — Docker Desktop Linux containers, внутри **Ubuntu 24.04.5 LTS, ROS2 Jazzy и Python 3.12**. Дополнительно чистые ядра и HTTP проверялись на Windows с Python 3.12.15.

## Автоматические тесты

`python -m pytest -q`: **47 passed в каждой версии**, включая отдельный запуск каждого набора в Ubuntu-контейнере. Проверены карта, физика, диспетчер, интеграция с детерминированными часами, HTTP и WebSocket. Это функциональные тесты; в большинстве из них ROS-транспорт подменён in-memory адаптером, а физика и планирование остаются настоящими.

Набор включает:

- точное соответствие обеих карт схемам, связность и отсутствующие рёбра;
- посещение каждого узла обеих карт одиночным роботом;
- движение назад, поворот, скорости колёс, стены и столкновения роботов;
- lease, manual deadman, застревание и возвращение к графу;
- встречные цели, уступание, освобождение занятой цели, обход поломки;
- сохранение ребра при stop/потере связи/ошибке, восстановление посреди ребра;
- последовательности команд и состояний, reboot и перестановки reset;
- дальние уникальные цели, последовательный fallback сложных операторских заказов;
- валидацию HTTP, WebSocket и метрики.

`ruff check warehouse tests tools launch setup.py` — без замечаний. `node --check warehouse/static/app.js` — успешно. Python AST обеих версий совпадает после удаления документационных строк; дополнительно версия без комментариев проходит те же тесты. Единственное предупреждение pytest — `DeprecationWarning` внутри зависимости Starlette/AnyIO; ошибок тестов нет.

## Стресс без реального ожидания

Команда: `python tools/stress.py --seconds 600 --seeds 3`. Это шесть запусков настоящей физики и диспетчера с ускоренными детерминированными часами, **без DDS**. Проверка выполнялась примерно за 3.5 секунды на данной машине; это результат стенда, а не обещание времени на любом оборудовании.

|---|---:|---:|---:|---:|---:|---:|
| normal | 3 | 0 | 55 | 400 | 0 | 0 |
| normal | 3 | 1 | 50 | 383 | 0 | 0 |
| normal | 3 | 2 | 54 | 397 | 0 | 0 |
| hardcore | 5 | 0 | 37 | 359 | 0 | 0 |

Суммарно **266 заданий, 2227 переходов, 3600 секунд модельного времени**. Физических столкновений не было; минимальное расстояние между центрами во всех этих прогонах — 2 м при защитном радиусе 0.5 м. Последний сценарий проверяет практическую неполноту Cooperative A*: один случайный набор не был принят, автоматические цели перевыбраны, движение продолжилось. Ошибкой робота или столкновением такой отказ планирования не является.

## Настоящий ROS2 / DDS

Образ успешно собран через colcon и запущен штатным `ros2 launch warehouse_sim warehouse.launch.py`. `ros2 node list` обнаружил **`/warehouse_simulator`** и **`/warehouse_dispatcher`**. `ros2 topic info --verbose` подтвердил publisher/subscriber обоих топиков: RELIABLE/VOLATILE и lifespan 500 мс у команд, BEST_EFFORT у состояний. Данные передаются между двумя отдельными процессами.

Важная обнаруженная при проверке деталь: colcon вызывается через `/opt/venv/bin/python -m colcon`. У созданного entrypoint действительно shebang `#!/opt/venv/bin/python`, поэтому ROS launch видит FastAPI и остальные зависимости виртуального окружения.

`tools/live_smoke.py --ros` **успешно выполнен в обеих версиях**, через работающий HTTP → диспетчер → DDS → физику → телеметрию:

1. Обнаружение настоящих ROS-нод.
2. Завершение команды движения в соседний узел.
3. Двустороннюю потерю связи, безопасную остановку, сохранение ребра и продолжение.
4. Застревание, сброс ошибки, ручной поворот, остановку и возврат к автоматике.
5. Включение троттлинга и восстановление свежей телеметрии.
6. Сложный склад с пятью роботами и завершёнными заданиями «Тёмного цеха».

Docker healthcheck после начальной телеметрии — `healthy`. После теста возвращён обычный склад с тремя роботами. При завершении любого из основных ROS-процессов launch останавливает второй; аварийный рестарт мира не маскируется как продолжение прежней физической сцены.

Отдельно проверены `docker compose up -d --build`, `docker compose stop` и повторный `start`. Оба ROS-процесса завершаются штатно (`process has finished cleanly`), HTTP-сервер выполняет application shutdown. Для передачи сигнала Docker запускает `exec ros2 launch`, а `STOPSIGNAL SIGINT` соответствует штатной остановке ROS launch. После рестарта healthcheck снова успешен.

## Браузер

Интерфейс проверен в headless Microsoft Edge/Chromium через Chrome DevTools CLI, на настоящем приложении в ROS-контейнере. Проверены:

- перемещение, парковка, stop/resume;
- W/S вперёд/назад, A/D поворот, в том числе русская раскладка;
- нулевая скорость после keyup и потери фокуса; остальные роботы неподвижны при manual;
- обе карты, пять роботов, случайные задания;
- STUCK и удерживаемое ребро, link loss и восстановление, throttle;
- размеры окна 1440, 768 и 390 px без переполнения страницы;
- отображение корпуса, колёс, направления, графа и физических стен;
- отсутствие ошибок JavaScript в консоли после загрузки.

Во время проверки устранена обратная связь между размером canvas и flex-контейнера: backing pixels больше не меняют размеры родителя. Также устранён сброс операторских настроек при каждом снимке состояния. Скриншоты исходного стенда сохранены отдельно в `artifacts/ui.png` и `artifacts/ui-mobile.png`; исходные архивы не требуют этих изображений.

## Что эти проверки не доказывают

Это не математическое доказательство достижимости любых совместных целей и не испытание сотен роботов. Не проверялись реальное оборудование, инерция/скольжение, внешний MQTT/VDA5050 и аппаратная аварийная остановка. Ограничения планировщика и физически невозможные конфигурации описаны в ARCHITECTURE.md и REQUIREMENTS.md, без безусловного обещания движения через перекрытый единственный проход.
