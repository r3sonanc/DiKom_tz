# Проверки, измерения и запуск на Ubuntu

Порядок работы: восстановить тесты → воспроизвести дефекты → измерить исходный код
→ исправить проверки физики → оптимизировать измеренные расходы API → повторить проверки.
Координация маршрутов, общий раунд, перебор приоритетов и частоты управления сохранены.

`hardcore` — внутреннее имя второй карты, которая в интерфейсе называется
«Узкие коридоры». `normal` — «Обычный склад».

Обоснование защиты от столкновений и её предпосылки находятся в [SAFETY.md](SAFETY.md).

## Историческая проверка до доработки наблюдаемости

Зафиксированный прогон 27 октября 2026 года: **83 passed за 15,75 с**, без ошибок.
Единственное предупреждение — сторонний `DeprecationWarning` совместимости
Starlette/AnyIO, не связанный с физикой или результатом тестов.
Тогда стадия `runtime` имела статус `healthy`.
Историческая сквозная проверка ROS/HTTP/двух WebSocket-клиентов и семи сценариев
из `live_smoke.py` завершилась с `ok: true` в Ubuntu 24.04.5 LTS.
Это исходная точка сравнения, а не отчёт о новой доработке P0/P1.

## Доработка безопасности и наблюдаемости

Существующие тесты сохранены. Новые проверки добавляют состояния
`OFFLINE → RECOVERING → ONLINE`, сохранение последнего разрешённого участка,
неожиданный reboot посреди перехода и отказ продолжать движение до подтверждения.
Обычный возврат связи не создаёт новую миссию; подтверждённое завершение перехода
не запускает его повторно. Перезапуск требует явного подтверждения оператора.

Дополнены проверки счётчиков переходов, дедупликации телеметрии и событий,
структурированных UTC-логов и двух независимых уровней health check.
Потеря одного робота после начальной синхронизации не превращает HTTP-сервис
в неработающий, пока от остальных есть свежая телеметрия. Отсутствие данных
от всех роботов более трёх секунд, остановленный контроллер или транспорт
дают HTTP 503. Флот при этом оценивается отдельными полями ответа.

Точные условия и временные границы проверок — в [ACCEPTANCE.md](ACCEPTANCE.md).
Результаты нового контрольного прогона сохраняются отдельно от исторических:
`docs/benchmarks/observability.json`, `final-pytest.txt`, `final-ubuntu-smoke.json`.
Итоговое число тестов, результаты CI и новые численные сравнения следует читать
по этим отчётам для проверяемого коммита, а не переносить из исходного прогона.

## Автотесты одной командой после сборки

Из папки проекта, одинаково в PowerShell и Ubuntu:

```sh
docker build --target test -t dikom-tests .
docker run --rm dikom-tests
```

Образ `test` содержит pytest/httpx. Обычный `docker compose up --build -d`
собирает последнюю стадию `runtime`, без установки этих dev-зависимостей.
Виртуальное окружение на компьютере для тестов не требуется.

Если уже используется Python 3.12 с зависимостями из `requirements-dev.txt`,
тот же набор запускается как `python -m pytest -q`.

## Что проверяется

| Файл | Проверки |
|---|---|
| [test_map.py](../tests/test_map.py) | Карты, узлы, парковки, рёбра и расстояния |
| [test_robot.py](../tests/test_robot.py) | Приказы, движение, lease, стены, ошибки, ручной режим, ревизии и reset |
| [test_dispatcher.py](../tests/test_dispatcher.py) | Встречные маршруты, разъезд, временные резервы, подтверждения, ошибки и восстановление |
| [test_integration.py](../tests/test_integration.py) | Совместная работа физики и диспетчера на модельных часах |
| [test_safety.py](../tests/test_safety.py) | Независимая геометрия полной дуги/отрезка, регрессии и длительные прогоны |
| [test_api.py](../tests/test_api.py) | HTTP, WebSocket, валидация запросов и представление состояния |
| [test_snapshot.py](../tests/test_snapshot.py) | Свежесть, изоляция данных, кэш, reset, несколько клиентов и медленный отправитель |
| [test_recovery.py](../tests/test_recovery.py) | Восстановление связи, reboot, удержание ресурсов, события и счётчики диспетчера |
| [test_observability.py](../tests/test_observability.py) | Метрики, структурированные логи, service/fleet health и частичная потеря связи |

Планировщик дополнительно проверяется на всех **288 назначениях** двух роботов
на четырёхузловом цикле и линии. Каждый возвращённый план проверяется независимо
на конфликты узлов, встречные переходы и пересечение резервируемых концов рёбер.
Для невозможного или не найденного назначения допустим безопасный отказ.

Длительные геометрические сценарии включают:

- 8 прогонов по 600 модельных секунд на обеих штатных картах;
- 3 прогона по 180 секунд с потерями, задержками, дубликатами и перестановкой
  сообщений в обоих направлениях;
- 80 сценариев ручного управления, встречные задачи, узкие коридоры и большой `dt`;
- отдельные проверки доводки к узлу и привязки при сбросе ошибки.

Геометрический oracle проверяет каждый принятый подшаг целиком, используя
экстремумы дуги и ближайшие точки к соседям. Он не вызывает production-проверку
`_collision()` как источник ожидаемого результата. Проверяются также положения
после каждого последовательного обновления робота и неизменность при отказе.
Радиус описанной окружности — 0,5 м; требование к центрам — расстояние не меньше 1 м.

Три добавленные регрессии сначала падали на исходной физике. После исправлений
проверяется хорда с запасом дуги у стен, положительный численный запас у роботов
и геометрическая проверка перед доводкой к конечному узлу.
Число прогонов не является доказательством для любых вещественных входных данных;
границы поддерживаемой модели перечислены в [SAFETY.md](SAFETY.md).

## Что оптимизировано

1. `FleetRuntime.reset()` один раз создаёт словарь неизменной карты.
2. `snapshot_json()` хранит одну готовую JSON-строку для нескольких наблюдателей.
   Временной интервал кэша — 100 мс; шаг контроллера, события и команды
   инвалидируют его немедленно. История снимков не накапливается.
3. Даже без новой телеметрии время обновляет кэш: возраст состояния продолжает расти,
   а робот становится offline. На принятие решений диспетчером этот кэш не влияет.
4. Публичный `snapshot()` остаётся свежим и возвращает независимые изменяемые данные.
5. `/metrics` берёт счётчики напрямую, без построения карты и полного состояния.
6. Каждый WebSocket-клиент отправляет данные отдельно с прежним тайм-аутом;
   медленный клиент не останавливает отправку остальным.

Перебор приоритетов, независимое продвижение без раунда и пространственный индекс
не внедрялись: при пяти роботах измерения не обосновали усложнение координации.
Пространственный индекс также не устраняет худший случай `O(R²)`, когда все рядом.

## Историческое сравнение до и после кэширования

Исходные данные: [before.json](benchmarks/before.json), [after.json](benchmarks/after.json).
Инструмент: [tools/benchmark.py](../tools/benchmark.py).
Оба отчёта относятся к этапу кэширования до добавления новых состояний и метрик.
Новый контрольный отчёт `observability.json` сравнивается с ними при тех же картах,
seed, длительности и числе условных клиентов.

Одинаковые условия: Python 3.12.3, Ubuntu 24.04 в Docker/WSL2,
600 модельных секунд, seeds 0/1/2, три повтора, 200 кадров снимков.
Моделирование ядра выполняется напрямую в памяти, без DDS/HTTP/браузера.
Условные WebSocket-клиенты последовательно запрашивают строку в рамках
одного временного кадра; сетевой I/O и реальные задержки клиентов не измеряются.

| Клиенты | Подготовка кадра p50 до, мс | После, мс | p95 до → после, мс |
|---|---|---|---|
| 1 | 0,094515 | 0,050656 | 0,147531 → 0,069692 |
| 10 | 1,045293 | 0,052810 | 1,656463 → 0,080132 |
| 50 | 4,766875 | 0,060459 | 5,704648 → 0,111802 |

Для 50 клиентов это примерно **79× меньше времени построения и JSON-кодирования
кадра в данном измерении**. Сетевая передача по-прежнему требует отправить
полный снимок каждому клиенту; весь WebSocket или всё приложение в 79 раз не ускорились.

Пиковые временные Python-выделения при подготовке снимков, КиБ:

| Клиенты | До | После |
|---|---|---|
| 1 | 41,513 | 43,187 |
| 10 | 35,458 | 30,321 |
| 50 | 35,409 | 30,272 |

`tracemalloc` для снимков включается **после** создания runtime. Эти значения
не включают заранее созданный постоянный кэш карты, полную память процесса,
DDS и сетевые буферы. Поэтому универсальное уменьшение RAM/RSS не заявляется.
Общий кэш добавляет одну карту `O(V+E)` и одну строку `O(D)`, где `D` — размер снимка.

Само вычислительное ядро в этих шести сценариях стало примерно на 2,6–7,4% медленнее
после дополнительных проверок безопасности. Число завершённых задач и отказов поиска
в каждом сценарии совпало с исходным; ошибок роботов не было.
В сценарии `hardcore`, seed=2 в обоих вариантах зарегистрирован один безопасный
отказ поиска — это не столкновение и не ошибка робота.

Пример повторения замера:

```sh
docker run --rm dikom-tests python tools/benchmark.py --seconds 600 --seeds 0 1 2 --repeats 3 --profile
```

Время без профилировщика и время из `cProfile` сравнивать напрямую нельзя.
Для ядра p95 по трём повторам фактически отражает максимальный из трёх замеров,
а не надёжную оценку хвоста распределения длительностей.

В новом контрольном замере дополнительно фиксируются длительности тиков диспетчера
и планирования: последние значения и агрегаты не заменяют распределение замеров.
Сравниваются завершённые миссии и ошибки на обеих картах, а не только время кадра.

## CI и наблюдаемость

Workflow [tests.yml](../.github/workflows/tests.yml) запускается при push в `main`
и pull request к `main`, собирает Docker test stage, проверяет импорты и выполняет
полный набор pytest. Состояние job в GitHub Actions — отдельное доказательство
для конкретного коммита; здесь не предполагается, что ещё не выполненная job успешна.

Метрики доступны по `/metrics` без сборки полного WebSocket-снимка:

| Метрика | Что считать |
|---|---|
| `warehouse_link_loss_events_total` | Переход ранее известного робота в OFFLINE; начальное ожидание не является потерей |
| `warehouse_link_recovery_events_total` | Первое принятое свежее состояние после OFFLINE; это ещё не разрешение движения |
| `warehouse_offline_robots` | Текущее число роботов без свежей телеметрии |
| `warehouse_fleet_safety_stops_total` | Вход в новый эпизод защитной остановки, а не каждый stop/тик |
| `warehouse_robot_errors_total` | Появление/изменение ошибки в принятом состоянии робота |
| `warehouse_planning_duration_seconds` | Длительность последнего фактического планирования |
| `warehouse_planning_duration_seconds_sum`, `_count` | Суммарное время и число планирований; по ним можно вычислить среднее |

Старые метрики сохранены. Счётчики сцены сбрасываются при reset. Журнал API
ограничен 100 событиями на экземпляр runtime и исчезает при рестарте процесса;
это не персистентная история нескольких запусков.
Повторы и запоздавшая телеметрия не увеличивают счётчики повторно.

Логи имеют UTC-время, уровень, ID робота, код события и причину, например:

```text
2026-10-27T18:42:15.000Z | WARNING | robot2 | LINK_LOST | telemetry timeout
2026-10-27T18:42:17.000Z | INFO | robot2 | LINK_RECOVERED | fresh telemetry received
```

Коды: `LINK_LOST`, `LINK_RECOVERED`, `FLEET_SAFETY_STOP`, `ROBOT_RESTARTED`,
`ROBOT_ERROR`, `ERROR_CLEARED`, `FLEET_RESUMED`, `PLANNING_FAILED`.
Сброс ошибки регистрируется после подтверждения роботом, а не по факту HTTP-запроса.
Повторяющийся отказ планирования с той же причиной не записывается на каждом тике.
Существующий журнал UI сохранён; его элементы дополнены `code`, `robot_id`, `reason`.

## Проверка работающего ROS и Ubuntu

```sh
docker compose up --build -d --wait
docker compose exec warehouse cat /etc/os-release
docker compose exec warehouse bash -lc "source /workspace/install/setup.bash && ros2 node list"
docker compose exec warehouse bash -lc "source /workspace/install/setup.bash && python /workspace/src/warehouse_sim/tools/live_smoke.py --ros"
```

`live_smoke.py` заменяет текущую сцену. Он проверяет реальный HTTP → диспетчер →
ROS → симулятор → телеметрия, двух WebSocket-наблюдателей, потерю связи,
остановку и продолжение с сохранённым участком, застревание/сброс, ручной поворот,
замедление связи и «Тёмный цех» с пятью роботами на сложной карте.
В конце создаётся обычный склад с тремя роботами.

Это запуск в **Ubuntu 24.04.5 LTS** с Python 3.12.3 и ROS2 Jazzy.
Docker здесь использует ядро WSL2. Отдельной установленной Ubuntu-дистрибуции
или Ubuntu VM в доступной среде нет; запуск на отдельном нативном Ubuntu-хосте
не заявляется. В контейнере проверяется нужная среда пользовательского пространства.

Результат живой проверки сохраняется в [ubuntu-smoke.json](benchmarks/ubuntu-smoke.json).
Итоговый вывод полного pytest-прогона — в [pytest.txt](benchmarks/pytest.txt).

Сложность после правок, включая память планировщика и сетевых соединений,
разобрана в [таблице SAFETY.md](SAFETY.md#сложность-после-кэширования-api).
