# Симулятор склада и диспетчер роботов
Двумерный симулятор склада с системой управления флотом мобильных роботов. Проект включает две карты, виртуальных дифференциальных роботов, кооперативное планирование маршрутов,\
веб-интерфейс оператора, имитацию отказов и механизмы безопасной остановки и восстановления.

Стек: Python 3.12, ROS2 Jazzy (`rclpy`, DDS), FastAPI, WebSocket, HTML/CSS/JavaScript, Docker, pytest.

## Возможности
- **Две карты:** обычный склад (`normal`, 1-3 робота) и «Узкие коридоры» (`hardcore`, 1-5 роботов), с навигационными узлами, рёбрами, парковками и внешними стенами.
- **Автоматические задания:** отправка к узлу, поиск доступной парковки, ожидание освобождения участков и согласованное движение нескольких роботов.
- **Ручное управление:** движение вперёд/назад и повороты через WASD или экранные кнопки. При ручном управлении остальных роботов автоматика приостанавливается.
- **«Тёмный цех»:** непрерывное назначение случайных удалённых целей после завершения предыдущих миссий.
- **Имитация отказов:** застревание, потеря связи и замедление обмена сообщениями для отдельного робота.
- **Восстановление:** сохранение резервов опасного участка, проверка свежести телеметрии, управляемое возобновление движения после потери связи или перезапуска робота.
- **Наблюдаемость:** статусы роботов, события и метрики, проверка работоспособности API, отдельная индикация связи браузера и роботов.

## Быстрый запуск
Требуется Docker с поддержкой Linux-контейнеров:

- **Ubuntu 24.04:** Docker Engine и Docker Compose v2.
- **Windows:** Docker Desktop в режиме Linux containers.

Python и ROS2 на хост устанавливать не нужно: зависимости входят в Docker-образ. Для первой сборки необходим доступ к интернету; порт `8000` должен быть свободен.

В корне проекта:

```bash
docker compose up --build -d --wait
```

Откройте **http://localhost:8000**. По умолчанию запускается обычный склад с тремя роботами.

```bash
# Состояние контейнера
docker compose ps

# Журнал приложения
docker compose logs -f warehouse

# Остановка
docker compose down
```

При следующих запусках, если образ уже собран, достаточно `docker compose up -d`.

> **Важно:** состояние сцен, задач и счётчиков хранится в оперативной памяти. Перезапуск приложения создаёт новую симуляцию.

### Настройки сцены
Карту и количество роботов можно изменять в интерфейсе кнопкой **«Новая симуляция»**. Для выбора начальной сцены доступны переменные окружения `WAREHOUSE_MAP` (`normal` или `hardcore`) и `WAREHOUSE_ROBOTS` (от 1 до числа парковок выбранной карты).

## Управление через интерфейс
1. Выберите робота и целевой узел на карте или в списке, затем нажмите **«Отправить»**.
2. Команда **«На парковку»** назначит свободную парковку.
3. **«Остановить»** приостанавливает весь флот; **«Возобновить»** продолжает работу после необходимых проверок.
4. **«Тёмный цех»** включает автоматическую выдачу последовательных случайных заданий.
5. Для ручного режима используйте **W/S** (вперёд/назад) и **A/D** (поворот). Отпускание клавиш, потеря фокуса и прекращение команд приводят к остановке по предусмотренным защитным механизмам. Для возврата к автоматической навигации робот должен находиться на графе.
6. В разделе проверки отказов можно включить **застревание**, **потерю связи** и **замедление обмена**. После застревания сначала отключите имитацию, затем сбросьте ошибку.

## Архитектура
Диспетчер и симулятор выполняются в **разных процессах ROS2** и обмениваются JSON-сообщениями внутри `std_msgs/msg/String` через DDS.

```text
Браузер (HTML / CSS / JS)
        |  REST API                  ^  WebSocket /ws
        v                            |
FastAPI / FleetRuntime / Dispatcher
        |                            ^
        v  /warehouse/commands       |  /warehouse/states
       RosTransport <----------------+
        |                            ^
        v                            |
ROS2 SimulatorNode / WorldCore / RobotCore
```

- **`warehouse/map.py`** - граф двух складов, парковки и геометрия карты.
- **`warehouse/robot.py`** - команды роботов, двумерная кинематика, проверки столкновений, ошибки и телеметрия; `WorldCore` объединяет роботов в одну сцену.
- **`warehouse/ros_simulator.py`** - ROS2-нода `/warehouse_simulator`, расчёт движения и публикация состояний.
- **`warehouse/dispatcher.py`** - постановка целей, кооперативное планирование, резервы, согласование переходов и обработка отказов.
- **`warehouse/transport.py`** - ROS2-нода `/warehouse_dispatcher`, публикация команд и получение телеметрии.
- **`warehouse/api.py`** - FastAPI, управляющий цикл, REST, WebSocket, события, состояние и метрики.
- **`warehouse/static/`** - веб-интерфейс и отрисовка карты в Canvas.
- **`launch/warehouse.launch.py`** - запуск ROS2-компонентов.

Физический цикл запускается с частотой **50 Гц**, типовая телеметрия и цикл диспетчера - **10 Гц**, браузер получает снимки приблизительно **5 раз в секунду**.

### Путь команды
После `POST` с целевым узлом диспетчер сохраняет задачу, рассчитывает согласованный маршрут и выдаёт роботу разрешение **на один переход между соседними узлами**. ROS2-симулятор принимает приказ, изменяет положение робота и публикует телеметрию. Диспетчер подтверждает завершение перехода по полученному состоянию и только затем продвигает соответствующий раунд. Браузер получает новый снимок через WebSocket.

Успешный HTTP-ответ означает **принятие команды сервером**, а не физическое завершение миссии.

## Маршрутизация и безопасность

### Кооперативное планирование
Склад представлен графом узлов и разрешённых рёбер. `CooperativePlanner` использует A*-поиск в пространстве **«узел, шаг плана»** с расстояниями BFS в качестве эвристики. План может включать ожидание на месте. Для каждого перехода резервируются оба конца ребра на соответствующем шаге; так предотвращаются конфликты занятия одного узла и встречные перемещения по узкому ребру.

Маршруты нескольких роботов строятся совместно с учётом ранее назначенных резервов. При необходимости меняется порядок приоритетов, робот может уступить дорогу либо задача выполняется поэтапно. Переходы согласованного раунда подтверждаются **реальной телеметрией**, а не ожиданием фиксированного времени поездки.

Поиск ограничен по горизонту и бюджету вычислений. Если безопасное расписание не найдено в этих пределах, диспетчер не выдаёт конфликтующее разрешение; существование маршрута во всех конфигурациях не гарантируется.

### Геометрический контроль
Вторая независимая защита действует внутри симулятора: перед изменением координат проверяется предполагаемая траектория относительно внешних стен и остальных роботов. Корпус 0,8 × 0,6 м консервативно представлен описанной окружностью радиусом **0,5 м**.

Проверяется не только конечная точка шага, но и участок движения. Для движения по дуге используется геометрический запас, предотвращающий пропуск столкновения между начальной и конечной позициями. При опасном перемещении координаты не изменяются, скорости обнуляются и регистрируется ошибка.

Расчёт мира последовательный: перед обновлением каждого робота учитываются текущие положения остальных. Эти гарантии относятся к двум штатным картам и предусмотренной модели симулятора.

### Потеря связи и восстановление
При отсутствии принятой свежей телеметрии более **1,5 с** робот переходит в `OFFLINE`. **Весь флот переводится в защитную остановку.** Последний разрешённый участок недоступного робота (включая концы ребра) остаётся зарезервированным до подтверждения его положения; один только тайм-аут резервы не снимает.

У каждого робота также есть локальный *lease* разрешения движения: **0,9 с** для автоматического и **0,35 с** для ручного управления. Без продления разрешения робот прекращает движение на следующем физическом шаге даже в том случае, если команда `stop` не дошла.

Свежая телеметрия после отказа переводит робота в `RECOVERING`. Перед возвратом в `ONLINE` проверяются факт остановки, координаты, узел или ребро, активный приказ, ошибки и конфликты резервов. При кратковременном обрыве без перезапуска после этих проверок возможно автоматическое продолжение; при изменении **`boot_id`** требуется явная команда оператора **«Возобновить»**. Флаг `recovery_ready` показывает готовность к подтверждению, но сам по себе не разрешает движение. Сервер повторно проверяет состояние всего флота при `resume`.

Сообщения защищены идентификаторами и порядковыми номерами: `command_id`/`command_seq` для приказов, `seq`/`boot_id` для телеметрии, `world_id`/`reset_seq` для сцены. Отметка источника `sim_time` помогает отвергать задержанные состояния даже с возрастающим `seq`. В текущем развёртывании для неё предполагаются общие монотонные часы процессов на одном хосте.

Статусы `OFFLINE`, `RECOVERING`, `ERROR` и `PAUSED` отображаются раздельно. Последняя известная, но не подтверждённая позиция визуально выделяется. Соединение **браузер ↔ сервер** через WebSocket контролируется отдельно от связи **диспетчер ↔ робот**.

> В текущей версии **не реализовано** продолжение движения остальных роботов при потере связи с одним роботом только за счёт локальной блокировки участка. Используется глобальная защитная остановка вместе с сохранением локальных резервов.

## API и наблюдаемость
FastAPI предоставляет интерактивную схему HTTP API по адресу **http://localhost:8000/docs**.

| Метод | Адрес | Назначение |
|---|---|---|
| `GET` | `/` | Веб-интерфейс |
| `GET` | `/api/health` | Состояние сервиса и флота |
| `GET` | `/api/state` | Текущий снимок склада |
| `POST` | `/api/reset` | Новая карта и число роботов |
| `POST` | `/api/robots/{robot_id}/commands` | `move`, `park`, `stop`, `resume`, `manual`, `clear_error` |
| `POST` | `/api/robots/{robot_id}/faults` | Имитация отказов |
| `POST` | `/api/dark-factory` | Управление «Тёмным цехом» |
| `GET` | `/metrics` | Метрики в текстовом формате Prometheus |
| `WS` | `/ws` | Поток снимков состояния для браузера |

Проверить работу сервиса можно командой:

```bash
curl http://localhost:8000/api/health
```

**HTTP 200** и `ok: true` означают, что контроллер и ROS2-транспорт работоспособны, начальная синхронизация завершена и от флота поступала свежая телеметрия. Если один робот недоступен, но от остальных поступают данные, сервис может оставаться доступным с HTTP 200: число недоступных роботов и `safety_stop` отражаются отдельно в `fleet`. При отсутствии телеметрии от всех роботов более трёх секунд либо остановке контроллера/транспорта возвращается **HTTP 503**.

Метрики включают количество завершённых задач и переходов, вызовов и отказов планировщика, потерянных и восстановленных соединений, аварийных остановок, ошибок роботов, число `OFFLINE`-роботов и длительности планирования. События регистрируются с UTC-временем, уровнем, идентификатором робота и кодом причины. Повторные сообщения не должны создавать повторный учёт одного и того же эпизода отказа.

Подготовка карты и JSON-снимка оптимизирована: карта сериализуется один раз для текущей сцены, а WebSocket-клиенты могут использовать общую подготовленную JSON-строку. **Это оптимизация формирования снимка, а не сетевой передачи и не всего приложения.**

### Проверка ROS2

```bash
docker compose exec warehouse bash -lc "source /workspace/install/setup.bash && ros2 node list"
docker compose exec warehouse bash -lc "source /workspace/install/setup.bash && ros2 topic list"
```

Ожидаемые ноды: `/warehouse_simulator`, `/warehouse_dispatcher`. Основные топики: `/warehouse/commands`, `/warehouse/states`.

## Тестирование и воспроизводимость
Для автотестов используется отдельная стадия Docker `test`; обычный запуск выполняется на стадии `runtime` без зависимостей pytest/httpx.

```bash
docker build --target test -t dikom-tests .
docker run --rm dikom-tests
```

Помимо модульных тестов проведены опубликованные в исходном проекте сквозные проверки в контейнере Ubuntu 24.04 (Docker/WSL2):

- **HTTP - ROS2/DDS - физика - телеметрия - WebSocket**, включая двух независимых наблюдателей;
- движение, застревание/сброс ошибки, ручное управление, задержки и потерю связи;
- восстановление после перезапуска робота с удержанием резервов, подтверждением оператора и однократным завершением первоначальной миссии;
- браузерный сценарий восстановления и блокировки `resume`, пока другой робот недоступен;
- «Тёмный цех» с пятью роботами на карте «Узкие коридоры»;
- проверки HTTP 200 при частичной и HTTP 503 при полной потере свежей телеметрии.

Алгоритм планирования дополнительно проверен на **288 вариантах назначений** двух роботов на небольших графах. Геометрические тесты используют независимые проверки траекторий, а не только повторное обращение к производственной функции столкновений.

Интеграционные сценарии можно воспроизвести из работающего контейнера (тест изменяет текущую сцену):

```bash
docker compose exec warehouse bash -lc "source /workspace/install/setup.bash && python /workspace/src/warehouse_sim/tools/live_smoke.py --ros"
```

Для отдельной проверки восстановления после reboot предусмотрен `tools/ros_recovery_smoke.py`.

### Производительность

В историческом сравнении до и после кэширования подготовка **одного общего JSON-кадра для 50 условных клиентов** снизилась по медиане с **4,77 до 0,060 мс** (примерно в **79 раз**). Измерение исключает реальную сеть и не означает ускорения всего WebSocket-сервиса в 79 раз.

Контрольные прогоны выполнялись в течение 600 модельных секунд на обеих картах с тремя наборами случайных целей. Безопасные отказы планирования не трактуются как столкновения. На сложной карте в одном прогоне зафиксирован редкий тик диспетчера **106,9 мс**, превышающий номинальный период контроллера 100 мс; жёсткая гарантия времени реакции не заявляется.

## Ограничения
- Это 2D-кинематическая симуляция, а не физическая модель промышленного оборудования: отсутствуют масса, инерция, расчёт тормозного пути, шум датчиков, локализация и аппаратные системы аварийной остановки.
- Протокол команд и состояний - собственный JSON поверх ROS2, не полная реализация VDA5050. MQTT и Gazebo не используются.
- Задачи, состояние и история событий находятся в RAM; постоянного хранилища, восстановления миссий после перезапуска процесса и аутентификации нет.
- Контроль свежести `sim_time` предполагает общий монотонный clock domain; распределение процессов по разным физическим хостам потребовало бы дополнительных механизмов времени и проверки подлинности.
- Гарантии геометрической безопасности относятся к последовательной модели движения и двум штатным картам. Проверенные сценарии не являются формальной гарантией отсутствия столкновений на реальном оборудовании или при произвольном внешнем управлении.
- Планировщик имеет ограниченный бюджет поиска и может безопасно отказаться от назначения, даже если решение теоретически существует. Универсальное отсутствие тупиков и гарантированное выполнение каждой миссии не заявляются.
